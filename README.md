# ArthroScope Research Radar — Streamlit

Next.js/Cloudflare 버전을 Python + Streamlit으로 옮긴 것입니다. 기능은 동일합니다.

- 10개 정형외과 저널의 PubMed 초록 수집 (NCBI E-utilities)
- 무릎 논문만 추려 주제 분류 → 반기 비교 트렌드 → 연구 공백 기반 아이디어 생성
- 탐지된 공백을 **추천 연구기회**와 **구조적 공백**으로 나눠 표시 (아래 참고)
- 계열·저널별 범위 전환, 아이디어 저장, 보고서(.md) 다운로드
- Gemini로 아이디어 고도화 (선택)
- GitHub Actions 일일 스냅샷 (선택)

## 파이프라인

```
최근 12개월 PubMed 수집 (10개 저널)
→ 주제 클러스터링 + PROM 3층 등 facet 분류
→ 클러스터 × 공백 단위로 객관적 신호 탐지 (6개 카테고리 · 9개 탐지기)
→ 분야별 기준 결과변수 적합성 확인 → 애초에 공백이 될 수 없는 조합은 생성 차단
→ gap 단위 판정 (opportunity / structural / uncertain)
→ structural 차단
→ 후보 과생성 (10~15개)
→ PubMed 전체 재검색으로 선행연구 확인
→ 근거·독창성·임상 중요성·방법론·실현 가능성 5축 평가
→ 의미상 중복 제거
→ 전역 제약 아래 최고점 조합 선택
→ 최종 최대 5개
```

목표는 **논문이 적은 곳**을 찾는 것이 아니라, **중요하지만 아직 제대로 답하지 못했고 실제로 수행할 수 있는 질문**을 찾는 것입니다. 빈도가 낮다는 것은 공백 후보일 뿐입니다.

## 문헌 데이터는 두 코퍼스입니다

| | 범위 | 목적 |
|---|---|---|
| 트렌드 탐지 | 최근 12개월 · 10개 저널 | 증가하는 주제, 설계·결과변수 변화, 지금 비어 있는 곳 |
| 선행연구 검증 | 최근 10년 · PubMed 전체 | 이미 같은 연구가 있는지, 어디까지 갔는지 |

최근 1년만으로는 트렌드는 볼 수 있어도 **독창성은 판정할 수 없습니다.** 그래서 후보마다 저널 제한 없이 다시 검색합니다 ([radar/prior_art.py](radar/prior_art.py)).

일치 판정은 규칙으로 합니다. 여기서 LLM에 "같은 연구인가"를 물으면 확신도를 버린 것과 같은 문제가 다시 생깁니다. 다만 ESearch가 이미 같은 용어로 AND 검색하므로 필터는 검색보다 엄격해야 합니다 — 같은 조건을 그대로 재확인했을 때는 받아온 39편이 전부 통과했습니다.

결과를 세 단계로 나눕니다.

| 단계 | 조건 |
|---|---|
| `direct` | 대상 클러스터와 공백 지표가 **둘 다** 그 논문의 주제이고, 대상군·비교군 조건까지 맞음 |
| `adjacent` | 둘 중 하나만 주제이거나, 공백 지표가 언급되지만 중심은 아님 |
| `background` | 검색에는 걸렸으나 주제만 같음 |

독창성 점수는 `direct` 편수만 씁니다. **검색 0건은 높은 독창성이 아니라 `미측정`입니다** — 검색식이 좁아 실패했을 가능성이 더 큽니다.

## 분석 단위는 클러스터가 아니라 `클러스터 × 공백`입니다

한 클러스터 안에도 서로 다른 공백이 있고, 판정도 달라집니다.

```
감염
├─ PROM 부족          → structural 가능성 (1차 결과가 감염 박멸이므로)
├─ 직접 비교 부족      → opportunity 가능성
└─ 장기 재감염 자료 부족 → opportunity 가능성
```

클러스터 전체를 한 번에 판정하면 이 셋이 같은 판정을 받습니다.

## 공백 카테고리 6종

| 카테고리 | 의미 |
|---|---|
| `outcome_measurement` | 결과 측정·해석의 부족 (MCID·PASS·표준화 지표) |
| `methodology` | 연구설계의 한계 (후향적 결과의 전향적 검증) |
| `comparator` | 필요한 직접 비교 부재 |
| `population_external_validity` | 특정 집단·외부검증 부족 |
| `clinical_utility_implementation` | 정확도 향상이 실제 진료에 도움이 되는지 |
| `longterm_durability` | 장기 결과 부족 |

`technology`는 공백의 종류가 아니라 연구 대상이므로 카테고리로 두지 않습니다. 로봇 연구도 직접 비교가 없으면 `comparator`, 환자 결과로 이어지는지 모르면 `clinical_utility_implementation`, 장기 자료가 없으면 `longterm_durability`입니다.

## PROM은 세 층으로 나눠 봅니다

| 층위 | 묻는 것 | 용어 |
|---|---|---|
| 1 측정 | 환자 점수를 실제로 수집·보고했는가 | KOOS, WOMAC, OKS, FJS, PROMIS, EQ-5D … |
| 2 임상적 해석 | 그 변화가 환자에게 의미 있는가 | MCID/MIC/MID, SCB, PASS, responder |
| 3 측정오차 | 관찰된 변화가 측정오차보다 큰가 | MDC/SDC, SEM, 신뢰도 |

MDC는 MCID와 다른 개념이므로 층위 2에 합치지 않습니다. PROM 공백은 조건부 비율로 탐지합니다 — 해석 공백은 **PROM이 이미 충분히 보고되는 분야에서만** 발화합니다. 20편 중 3편만 PROM을 쟀는데 "그중 MCID 해석이 없다"는 것은 해석 공백이 아니라 표본 부족입니다.

화면에는 "초록 기준"임을 반드시 표시합니다. 본문이나 표에만 MCID 분석이 있을 수 있으므로 실제 사용률이라고 단정할 수 없습니다.

## 분야별 기준 결과변수를 먼저 적용합니다

[radar/vocabulary.py](radar/vocabulary.py)의 `CANONICAL_OUTCOMES`에 분야마다 원래 무엇을 1차 결과로 삼는지 적어 둡니다. 이것이 없으면 "PJI 연구에 PROM이 적다"를 공백으로 착각합니다.

`reviewed: False`는 전문가 확인 전 잠정값이라는 뜻입니다. 판정 프롬프트에 그대로 표시되고, 모델이 그 정의가 틀렸다고 보면 `uncertain`으로 판정하게 되어 있습니다.

형평성(`health_equity`)과 환자요인(`patient_factor`)도 분리했습니다 — 소득·보험·지역·언어에 따른 피할 수 있는 격차와, 나이·비만·동반질환의 예후 효과는 기준 결과변수가 다릅니다.

## 최종 선택은 전역 제약으로 합니다

점수 순으로 위에서 다섯 개를 자르면 같은 종류가 목록을 채웁니다. 실제로 그랬습니다 — "감염 연구의 결과가 환자 체감 회복으로", "AI 연구의 결과가…", "로봇 연구의 결과가…"가 나란히 올라왔습니다. 주제 단어만 바뀌고 연구 질문·설계·1차 결과변수의 구조가 같은 의미상 중복입니다.

그래서 세 단계를 둡니다 ([radar/selection.py](radar/selection.py)).

1. **자격 게이트** — 공백 유형 없음 · structural 판정 · 최소 통과점수 미달 · 독창성 미측정을 뺍니다
2. **중복 제거** — ① 같은 `클러스터:공백`이면 가장 강한 하나 ② 자기 클러스터 이름을 지웠을 때 문장 구조가 같으면 가장 강한 하나
3. **전역 제약 아래 최고점 조합 선택** — 개별 점수 합이 아니라 조합을 고릅니다

중복 제거 키는 **반드시 `클러스터 × 공백`**이어야 합니다. `gapId`만으로 묶으면

```
외래·회복 × 장기 안전성
비용·보건정책 × 장기 경제성
형평성 × 장기 회복 격차
```

가 전부 `longterm_followup` 하나로 뭉쳐 둘이 삭제됩니다. 서로 다른 연구 질문입니다. 같은 종류가 몰리는 것은 삭제가 아니라 카테고리 상한(≤2)으로 막습니다.

의미 중복 검사에서 지우는 것도 **자기 클러스터 이름뿐**입니다. 모든 주제 이름을 지우면 교차 공백의 두 번째 축(`× 감염` vs `× 로봇`)이 사라져 같은 실수를 반복하게 됩니다.

**최소 통과점수가 없으면 "5개 미만 허용"은 작동하지 않습니다.** 후보가 전부 양수 점수라 조합 최적화가 거의 항상 다섯 자리를 채우기 때문입니다 (`MIN_FINAL_SCORE`).

조합 수는 자격을 통과한 후보 수에 따라 달라집니다 — 14개에서 5개면 2,002가지, 15개면 3,003가지. 실제로 훑은 수는 화면과 `validate.py`에 표시됩니다.

```
최종               최대 5개
PROM/MCID/PASS     전체 최대 1개   (opportunity가 여럿이어도 올리지 않음)
동일 gap category  최대 2개
동일 source_gap_id 최대 1개
카테고리 다양성     가능하면 3종 이상
unknown·structural 선택 금지
근거 부족 시        5개 미만 허용
```

후보 15개에서 5개를 고르는 조합은 3,003가지뿐이라 greedy 대신 완전 탐색을 씁니다.

## 5축 평가

| 축 | 어디서 나오는가 |
|---|---|
| 근거 강도 | 통계 지표 (표본 충분성·효과크기·z·종합 근거 수준) |
| 독창성 | 선행연구 `direct` 편수. **없거나 검색 0건이면 `미측정`** — 검색식 실패 가능성이 더 크므로 높은 독창성으로 주지 않습니다 |
| 임상 중요성 | 판정 + 기준 결과변수 적합성 + 카테고리 |
| 방법론적 발전 | 공백 카테고리 |
| 실현 가능성 | 규칙 기반 |

opportunity에는 +2 가점을 줍니다. LLM이 주는 "확신도 4/5"는 최종 점수의 핵심으로 쓰지 않습니다.

독창성이 `미측정`인 후보는 최종에서 빼고 **검증 대기** 영역에 따로 보여줍니다. 선행연구 검증이 끝나면 후보로 돌아옵니다.

### PROM 공백은 막지 않고 누릅니다

`prom_role`이 `secondary`라는 것은 "중요하지 않다"가 아니라 "1차 결과가 아니다"라는 뜻입니다. 감염이 치료된 환자의 기능 회복은 1차 결과가 아니어도 물을 가치가 있습니다. 그래서 생성 자체를 막는 것은 `not_applicable`뿐입니다.

| prom_role | 처리 |
|---|---|
| `primary` | 그대로 후보 |
| `contextual` | 근거가 강할 때만 (표본 충분 + 효과크기 0.5 이상) |
| `secondary` | 후보로 올리되 **감점 2점** + 판정 필수 |
| `not_applicable` | 생성 차단 |

### 구조적 게이트는 6개 카테고리 전부에 걸립니다

구조적 공백은 PROM에만 생기지 않습니다. 판정 프롬프트에 카테고리마다 흔한 구조적 사유를 넣습니다 (`STRUCTURAL_PRIORS`).

- 도입 3년 된 기술에 10년 생존율이 없음 → `longterm_durability`의 구조적 사유
- 단일군 feasibility 연구에 비교군이 없음 → `comparator`의 구조적 사유
- 발생률 1%인 합병증에 무작위시험이 없음 → `methodology`의 구조적 사유

canonical outcome은 이 판정을 돕는 **입력**이지 판정 그 자체가 아닙니다.

## 공백을 나누는 기준

통계가 찾아낸 공백이 전부 연구 기회인 것은 아닙니다. 인공관절 감염 연구에 PROM이
적은 것은 연구가 부족해서가 아니라 그 분야의 1차 결과가 균 박멸과 임플란트 생존이기
때문입니다. 그래서 판정 단계를 거쳐 화면을 둘로 나눕니다.

- **opportunity** — 그 분야의 목적에 비추어 중요한데 실제로 비어 있다. 최종 후보가 됩니다
- **structural** — 통계적으로만 비어 있다. 최종에서 차단하고, 지우지 않고 **왜 추천하지 않았는지**와
  **그 분야가 실제로 쓰는 1차 결과**를 함께 별도 섹션에 남깁니다
- **uncertain** — 근거가 얇거나 기준 결과변수 적합성이 애매하다. 검토 대상으로 남기되 가점은 없습니다

"이미 답해졌는가"는 판정에서 뺐습니다. 최근 12개월 코퍼스로는 답할 수 없는 질문이라, 선행연구 검증 단계가 PubMed 전체를 다시 뒤져 따로 판단합니다.

각 판정에는 모델이 스스로 매긴 확신도 대신, 밖에서 관측한 네 가지를 붙입니다.

| 항목 | 어떻게 재는가 |
|---|---|
| 판정 안정성 | 같은 프롬프트를 주 모델로 5회 돌려 같은 판정이 나온 비율 |
| 모델 간 합의 | 두 번째 Gemini 모델(및 `OPENAI_API_KEY`가 있으면 OpenAI)의 판정과 일치하는지 |
| 시간적 근거 | 기간을 전반기·후반기로 나눠 다시 쟀을 때 공백이 좁혀졌는지·유지됐는지 |
| 표본 충분성 | 그 공백을 잰 문헌 수와 효과크기(Cohen's h) |

넷을 합쳐 **종합 근거 수준**(높음·중간·낮음)을 냅니다. 판정과 방향이 맞는 신호는
더하고 반박하는 신호는 뺍니다 — 예를 들어 구조적 공백이라면 공백이 그대로 유지돼야
판정을 지지하고, 연구기회라면 최근 반기에 실제로 좁혀지고 있어야 지지합니다.
아직 재지 않은 항목이 하나도 없으면 `미측정`으로 표시하고 등급을 매기지 않습니다.

## 실행

```bash
pip install -r requirements.txt
streamlit run app.py
```

## 설정 (선택)

`.streamlit/secrets.toml.example`을 `.streamlit/secrets.toml`로 복사해 채우거나, 같은 이름의 환경변수를 쓰면 됩니다.

| 키 | 용도 |
|---|---|
| `APP_PASSWORD` | 접근 암호. 설정하면 첫 화면에서 암호를 묻습니다. 비우면 잠기지 않습니다 |
| `NCBI_API_KEY`, `NCBI_TOOL_EMAIL` | 초당 요청 한도 3 → 10회, 초록 수집 병렬화 |
| `GEMINI_API_KEY`, `GEMINI_MODEL` | "AI로 고도화" 버튼 활성화 |
| `GITHUB_REPO`, `GITHUB_TOKEN`, `GITHUB_BRANCH` | 비공개 저장소의 `data/daily.json` 스냅샷 읽기 |

앱은 `data/daily.json`이 로컬에 있으면 그것을 먼저 보여주고, 없으면 GitHub에서 시도하고, 그것도 없으면 기본 1년 범위로 실시간 분석을 돌립니다. 사이드바의 운영 로그(`data/run_log.json`)도 같은 순서로 읽습니다.


### 재현성

실행마다 `data/run_manifest.json`이 함께 만들어집니다 — commit, 캐시 버전, 수집일, 저널 목록, PubMed 질의(수집·선행연구 각각), 코퍼스 PMID 전체, 임계값 전부, 사전·기준표·프롬프트·모델 버전, 그리고 네 가지 해시입니다.

| 해시 | 무엇이 바뀌면 달라지는가 |
|---|---|
| `corpusPmidsHash` | 수집된 논문 목록 |
| `corpusContentHash` | 제목·초록·저널·날짜 (PubMed의 사후 수정을 잡아냅니다) |
| `llmJudgmentHash` | 판정 결과 |
| `priorArtResultHash` | 선행연구 결과 |

해시는 키를 정렬하고 배열도 정렬한 정규 직렬화 위에서 계산하므로, 순서만 바뀌어서 달라지지 않습니다.

`corpusContentHash`는 "바뀌었다"는 사실만 알려줄 뿐 과거 내용을 복원하지 못합니다. 그래서 그 실행에 실제로 들어간 제목·초록 원본을 `data/corpus/corpus-{날짜}.json.gz`로 함께 남깁니다. 용량 때문에 저장소에는 커밋하지 않으니(`.gitignore`), 백테스트나 논문화를 염두에 둔다면 Release 자산으로 올려 두세요.

```bash
gh release create corpus-2026-08-24 data/corpus/corpus-2026-08-24.json.gz   --title "Corpus snapshot 2026-08-24" --notes "run_manifest.json의 corpusContentHash와 대조"
```

**전문가 평가는 manifest가 고정된 뒤에 시작하세요.** 사전이나 임계값이 바뀐 뒤의 결과와 섞이면 평가가 무의미해집니다. 평가 시에는 모델의 판정과 점수를 가리고 아이디어만 보여주는 편이 anchoring bias를 줄입니다.

`data/run_log.json`에는 실행마다 한 줄씩(수집 편수·공백 수·AI 갱신 여부·소요 시간, 실패했다면 그 사유) 쌓입니다. 앱 사이드바의 **운영 로그**가 이 파일을 그대로 읽어 마지막 수집 시각, 최근 7일 중 며칠이나 돌았는지, 실패가 있었는지를 보여줍니다. 스냅샷만으로는 "마지막 결과"밖에 알 수 없어 며칠째 멈춘 것을 눈치채기 어렵습니다.

`.github/workflows/daily.yml`이 매일 18:00 KST에 같은 스크립트를 돌려 커밋합니다. 저장소 Secrets에 `NCBI_API_KEY`, `NCBI_TOOL_EMAIL`, `GEMINI_API_KEY`를, Variables에 `GEMINI_MODEL`을 넣으세요.

공백 판정은 이 일일 작업에서만 돕니다(앱은 스냅샷의 판정을 읽기만 합니다). 그래서 판정단 설정도 앱의 `secrets.toml`이 아니라 이 작업의 환경변수로 줍니다.

| 환경변수 | 용도 |
|---|---|
| `GEMINI_JUDGE_MODEL_B` | 교차 검증용 두 번째 Gemini 모델. 비우면 `gemini-2.5-flash` |
| `OPENAI_API_KEY`, `OPENAI_JUDGE_MODEL` | 넣으면 다른 회사 모델까지 판정단에 들어갑니다 (기본 `gpt-4o`). 없으면 Gemini 두 모델로만 합의를 잽니다 |
| `GEMINI_FORCE=1` | 요일과 무관하게 Gemini 단계를 강제 실행. 판정 로직을 바꾼 직후에 씁니다 |

## Streamlit Community Cloud 배포

저장소를 연결하고 `app.py`를 메인 파일로 지정한 뒤, 앱 설정의 Secrets 란에 `secrets.toml` 내용을 붙여 넣으면 됩니다.

## 구조

```
app.py                 # 화면 (app/page.tsx)
radar/config.py        # 임계값·전역 제약. 백테스트로 조정할 값은 전부 여기
radar/vocabulary.py    # 용어 사전 · PROM 3층 · 분야별 기준 결과변수 · 공백 카테고리
radar/analysis.py      # 수집·분류·트렌드 + 9개 공백 탐지기
radar/judge.py         # gap 단위 판정(반복 실행·모델 간 합의)과 종합 근거 수준
radar/prior_art.py     # PubMed 전체 재검색으로 선행연구 확인
radar/selection.py     # 5축 평가 · 의미상 중복 제거 · 전역 제약 조합 선택
radar/ncbi.py          # E-utilities 호출·재시도 (lib/ncbi.ts)

```

### 캐시 무효화

사전이나 프롬프트를 고치고 버전을 안 올리면 옛 판정이 조용히 재사용됩니다. 캐시 키에는 다음이 전부 들어갑니다 (`radar/judge.py`의 `cache_versions()`).

```
prompt_version · keyword_dictionary_version · canonical_outcome_version · config_version · runs
```

`radar/vocabulary.py`나 `radar/config.py`를 고치면 해당 파일 맨 위의 버전을 올리세요.

판정 한 건에 주 모델 5회 + 나머지 판정자 1회씩을 씁니다. 제목만 보내는 짧은 프롬프트고
Gemini 단계 자체가 주 1회(금요일)만 돌기 때문에, 반복 비용보다 "확신도 4점 일색"을
없앤 값이 큽니다. `radar/judge.py`의 `JUDGE_RUNS`로 조절합니다.

원본과 다른 점: 저장한 아이디어는 브라우저 localStorage 대신 `data/saved_ideas.json`에 보관됩니다.
